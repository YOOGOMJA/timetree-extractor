## 1. Executive Summary

공식 export가 없는 TimeTree에서, 로그인된 사용자의 **개인·공유 일정을 손실 없이 Google/Apple Calendar로 옮겨주는** 로컬 전용 Chrome 확장. 성공은 "데이터를 보여주는 것"이 아니라 **"실제로 옳게 import되는 파일을 받고 가져오기를 끝내는 것"**.

## 2. Background & Context

- TimeTree는 공유/가족 캘린더로 끈끈하지만 **공식 내보내기가 없다** → 떠나거나 합치려는 사용자의 일정(특히 수년치 공유 일정)이 갇힌다. (`value-proposition.md`)
- 진짜 잡 = **마이그레이션**(TimeTree → 파일 → Google/Apple import). 현재 구현은 *파일 다운로드*에서 멈춰 **마지막 1마일(가져오기)이 비어 있다.** (`risky-assumptions.md` U1)
- 차별점: **로컬 전용**(남의 서버에 안 올림 — 온라인 변환기 대비 신뢰) + **충실도**(반복/시간대 보존, 무손실 가시화).
- ⚠️ **프레임 충돌(오픈 리스크)**: 본 PRD는 제품 지향이나, `decisions/0002-implementation-go-no-go.md`는 "비배포 연구 프로토타입"으로 못 박았다. 제품화하려면 0002 갱신 + 배포 경로가 선행 리스크.

## 3. Objectives & Success Metrics

**Goals**
1. 마이그레이션 잡 완주율 ↑ — 사용자가 "파일 받기"를 넘어 **Google/Apple import까지** 끝낸다.
2. import 정합 — 내보낸 ICS가 반복·시간대·공유 일정까지 **깨지지 않고 들어간다**.
3. 신뢰 — 무엇이 수집/제외됐는지 투명, 로컬 전용을 명확히.

**Non-Goals**
1. 서버/계정 연동/클라우드 동기화 — 안 함(로컬 전용은 기능이자 차별점).
2. TimeTree로의 역방향 import/쓰기 — 범위 밖.
3. 첨부 바이너리·참가자 PII export — 범위 밖(privacy 스펙).
4. (이번 Phase) Chrome Web Store 배포 — 별도 트랙(§7).

**Success Metrics**
| Metric | Current | Target | Measurement |
|--------|---------|--------|-------------|
| 실데이터 Google import 정합(반복/시간대/공유) | 미검증 | 핵심 케이스 100% | 실 ICS를 Google에 import해 수동 확인 |
| 마이그레이션 완주(파일→import) | 가이드 없음 | 가이드 제공 + 완주 가능 | 화면에 import 단계 존재 |
| "제외/이슈" 행동가능 카피 | enum→사람말(부분) | 100% "그래서 뭘" 포함 | 카피 리뷰 |
| (배포 후) 설치→첫 export 성공률 | N/A | ≥70% | 분석(배포 트랙에서) |

## 4. Target Users & Segments

- **1차: 마이그레이터** — TimeTree를 떠나거나 한 캘린더로 합치려는 개인/가족 대표. 기술 자신감 중. (현재 설치 장벽 U3로 사실상 기술 유저에 치우침 — 배포 트랙에서 해소 필요.)
- **2차: 아카이버** — 이탈 없이 공유/가족 일정의 로컬 사본을 원함. JSON/ICS 백업.

## 5. User Stories & Requirements

**P0 — Must Have**
| # | User Story | Acceptance Criteria |
|---|-----------|-------------------|
| P0-1 | 마이그레이터로서 내 개인·공유 캘린더를 한 번에 수집하고 싶다 | 수집 시 모든 접근 가능 캘린더(공유 포함) 표시·포함, 제외 없음 |
| P0-2 | 무엇이 수집/제외됐는지 한눈에 보고 신뢰하고 싶다 | 대시보드: 내보낼 N/전체 M/제외 D + 캘린더별·카테고리·이슈 |
| P0-3 | 제외/이슈가 **왜·괜찮은지** 알고 싶다 | 각 이슈에 "그래서 뭘"까지 카피(예: "Google이 못 읽는 형식이라 제외, 보통 안전") |

| P0-5 | 옮긴 일정이 깨지지 않길 바란다 | 반복/시간대/공유 import 정합 — 실데이터 1회 검증(스모크) |

## 6. Solution Overview (증분)

현재(대시보드 + ICS/JSON) 위에 **마지막 1마일과 신뢰 카피**를 더한다. 화면별 요구·상태(=화면 기획):

| 화면 | 잡 | 핵심 요소 | 상태(빈/오류) |
|---|---|---|---|
| 진입 | 시작·신뢰 | "캘린더 수집" hero, 로컬 전용 한 줄, 최근 내보내기 | 비-TimeTree→열기 버튼; 최근 없으면 섹션 숨김 |
| 수집(로딩) | 진행 | 진행 표시 | 실패→idle 조용히 fallback(현행) |
| **대시보드** | 검토·신뢰 | 충실도 hero + 캘린더별 + 카테고리 + **이슈(행동가능 카피)** | 이벤트 0/이슈 0 섹션 숨김 |
| 상세 | 확인 | 검색 + 전체 목록(가상화) | 검색 0건 안내(현행) |
| 내보내기 | 산출 | 형식 + "전송 안 함" 문구 + 내보내기 | 0건 차단 |
| **가져오기 가이드(신규 P0-4)** | 완주 | export 직후 "Google/Apple로 가져오기" 단계+링크 | — |
| 오류 | 회복 | 무엇이/어떻게 | 재시도 |

설계 방향: 기존 system-ui 일관, 충실도·이슈를 *신뢰 장치*로 1급. **가져오기 가이드가 이번 핵심 신규 화면.**

## 8. Timeline & Phasing
- **Phase 1 (지금, 증분)**: P0-3(이슈 행동가능 카피) + P0-4(가져오기 가이드 화면) + P1-3(전송 안 함 문구) + P0-5 검증(브라우저 실 import 스모크). → "기획 정확도+디자인 보완"의 직접 산출.
- **Phase 2**: P1-1(전체 기간 기본), P2-1(캘린더 토글).
- **배포 트랙(병행/후속)**: 0002 갱신 + Web Store/설치 경로(P2-2) + F1(내부 API 의존) 모니터링.
