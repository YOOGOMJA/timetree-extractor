# 위험 가정 색출 — TimeTree Exporter

> 2026-06-12. 악마의 변호인 분석(PM/디자이너/엔지니어 관점 × Value/Usability/Viability/Feasibility).
> 목적: "기획 정확도가 안 좋다"의 근원을 드러내기. 결론부터 — **가장 큰 문제는 개별 기능이 아니라 "이게 무슨 제품인가"의 프레임 불일치.**

## 🔴 0순위 — 프레임 불일치 (모든 것의 상류)

`value-proposition.md`는 이 도구를 **소비자 마이그레이션 제품**(이탈하는 TimeTree 유저 대상)으로 썼다. 그러나 프로젝트 제약(`decisions/0002-implementation-go-no-go.md`, `privacy-and-local-only-boundary.md`)은 이 도구를 **로컬 연구용 프로토타입 — 배포 없음(Chrome Web Store 없음), 서버 없음, 공개 없음**으로 못 박았다.

→ 두 프레임이 충돌한다. 비배포 연구 프로토타입이면 **실사용자 = 작성자 본인 + 소수 기술 유저**이고, "소비자 마이그레이터를 위한 세련된 대시보드"는 *틀린 프레임에 과투자*다. 반대로 진짜 제품을 노린다면 배포·ToS·세그먼트 검증이 0순위다.

**이 결정이 안 서면 아래 PRD·화면 기획·디자인이 전부 흔들린다.** (가장 큰 planning 부정확성의 정체.)

---

## Value (진짜 가치가 있나)

- **V1 (High risk)** "마이그레이터가 주 사용자" — 인터뷰 0건. 실제 설치자는 ① 호기심 1회성 ② 백업러 ③ 개발자일 수 있다. 잘못이면 화면의 성공 정의가 통째로 어긋남. *테스트: 5명 문제 인터뷰(왜 export를 원했나, 그 다음 뭘 했나).*
- **V2 (High)** "ICS가 Google/Apple에 깨끗이 import된다" — 충실도 작업(반복/시간대)은 했으나 **실제 Google 왕복 검증 미완**(#59 류 수동 smoke 남음). 이게 깨지면 가치 0. *테스트: 실데이터 ICS를 실제 Google Calendar에 import해 반복/시간대/공유 확인.*
- **V3 (Medium)** "export를 원할 만큼 사람들이 TimeTree를 떠난다" — TimeTree는 공유/가족으로 끈끈. 수요가 희박·1회성일 수 있음. *테스트: 검색량/커뮤니티 글("timetree export") 정량 확인.*

## Usability (쓸 수 있나)

- **U1 (High)** 마이그레이션은 **2앱 여정**(TimeTree→파일→Google import)인데 도구는 "파일 다운로드"에서 끝난다. 마지막 1마일(어떻게 import하는지)이 없어 잡이 미완. *테스트: 사용자에게 끝까지 시켜보고 어디서 막히나.*
- **U2 (Medium)** 대시보드의 "제외 4건/이슈"가 마이그레이터에겐 **행동 불가능한 불안**일 수 있음("뭐가 빠졌다는데 어쩌라고"). 신뢰 장치가 공포 장치로. *테스트: 이슈 카피를 "그래서 뭘 하면 되나"까지.*
- **U3 (High, 구조적)** **Web Store 미배포 → unpacked 확장 수동 설치**가 절대적 진입장벽. 비개발자는 실행조차 못 함. 사실상 사용자 = 기술 유저로 좁혀짐 → V1과 모순.
- **U4 (Medium)** 마이그레이터는 보통 "전체 기간"을 원하는데 기본 기간이 ±1년. 잡과 기본값 불일치 가능.

## Viability (조직/법/지속이 받쳐주나)

- **Vi1 (High, 의도된 제약)** 비배포·비서버·연구용 → "제품 viability"는 의도적으로 0에 가깝다. 이걸 소비자 제품처럼 기획하면 카테고리 오류(=프레임 0순위).
- **Vi2 (Medium)** TimeTree AUP/ToS — 내부 API 사용. 개인 규모는 무난하나 배포·대량은 선을 넘음(이미 제약됨).
- **Vi3 (Medium, 윤리)** 공유 캘린더 = **타인(가족)의 개인 일정**을 로컬 파일로. 내 접근권 내라 일반적으로 OK지만, "남의 데이터를 옮긴다"는 점은 명시적 동의 카피로 다뤄야(현재 1회 동의로 부분 충족).

## Feasibility (만들 수 있나/유지되나)

- **F1 (High)** 미문서 내부 API(`X-TimeTreeA` 등) 의존 → TimeTree가 바꾸면 **언제든 깨짐**. 장기 신뢰성 위험.
- **F2 (Medium)** 충실도 엣지(UNTIL/이동 override/>1MB)가 실 Google import에서 미검증(일부 #63 등으로 이슈화).
- **F3 (Low)** 대량 이벤트 fetch + AUP "과부하 금지" — 가상화는 했으나 fetch 정책 점검 필요.

## 우선 테스트 (Impact × 불확실성)

1. **프레임 결정**(0순위) — 작성자 결정 사항: 개인 유틸 / 연구 산물 / 제품 지향. *아래 모든 기획의 게이트.*
2. **V2 실 Google 왕복** — 가치의 생사. 브라우저로 즉시 가능.
3. **V1/U1 문제 인터뷰** — "왜 export했고 그 다음 뭘 했나" 5명(프레임이 '제품/유틸'이면).
4. **U3 설치 장벽** — 프레임이 '제품'이면 배포 경로(미배포 제약과 충돌) 재검토.

## 결론
"기획 정확도"가 낮게 느껴진 진짜 이유: **이 도구의 정체(프레임)를 정하지 않고 소비자 제품처럼 화면을 다듬어 왔다.** 프레임을 정하면 — 디자인의 성공 기준, 마지막 1마일(import 가이드) 유무, 이슈 카피, 기본 기간, 설치/배포까지 — 한 번에 정렬된다.
